# Application review — 2026-09-15

## Verified corrections
- Medical establishment registrations now use PocketBase record IDs and await directory persistence before reporting success.
- Failed request creation no longer produces a local-only successful request.
- Updating a missing/forbidden record no longer silently creates a duplicate.
- Request status, rating and profile save feedback follows successful server persistence.
- Provider and company forms remount when their asynchronously loaded owned profile changes.
- Session restoration requires a matching valid PocketBase token; roles are read from its record, not a local UI flag.
- Private service requests are no longer cached in localStorage. Logout clears requests and provider cache.
- Production API configuration requires HTTPS. Superusers do not see the customer self-deletion control.
- Deployed server rules prevent self-approval, ownership reassignment and direct provider rating manipulation.
- Request rules restrict status transitions to the assigned provider; customers can rate their own completed, unrated request.

## Verification performed
- TypeScript check, production Vite build and Capacitor synchronization passed.
- Live disposable-account integration test passed: provider/customer persistence, own profile edit, self-approval rejection, visibility after administrator approval, request delivery, accepted/completed transitions, customer rating, cascading request deletion.
- Test accounts and related records were deleted. No existing user records were intentionally changed.

## Remaining work / limits
- No physical Android device or full browser UI walkthrough was completed in this review.
- npm vulnerability audit could not reach the advisory endpoint; dependencies cannot be certified clean.
- Some administration mutations still optimistically update UI before persistence; network-failure UX needs further coverage.
- Registration creates the auth record before its professional profile. A second-step failure needs a profile-completion/recovery flow.
- Provider-wide rating aggregation remains unimplemented; individual request ratings are saved.
- Google OAuth, SMTP/password recovery, external image links and location permissions require separate end-to-end checks.
- Signing credentials previously found in Gradle configuration need secure externalization before release; this review produces a debug APK, not a Play-ready release.
- Prior support messages/complaints are not automatically linked to account deletion.
- This is a scoped code/backend review, not a claim that the application is defect-free or approved for Google Play.
